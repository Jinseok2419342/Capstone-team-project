## S2–S4 — 같은 물품의 등록·이동·회수 / 14쪽

현재는 사용자가 성공을 보고한 상태이며, 같은 물품의 사진·ID와 개별 원격 AI 응답을 저장한 발표용 증거는 없다. 아래 캡처는 새 확인 결과로 추가한다.

### 준비

- Pi를 켜고 실제 카메라가 연결된 관리자 화면을 연다. 기존 설치·공유 초대를 처음부터 반복할 필요는 없다.
- 확인하기 쉬운 물품 **하나**와 고정된 촬영 위치를 준비한다. 내장 예시 추가 버튼으로 만든 물품을 실제 카메라 등록 사례로 사용하지 않는다.
- 필요한 기존 기록이 있다면 초기화하지 않는다. 시작 화면 정리가 꼭 필요한 경우에만 데이터를 보존할지 먼저 판단한다. **시연 초기화는 모든 운영 물품·활동·알림·사진을 백업 없이 삭제한다.**
- 날짜, 물품명, 촬영 조건, 실제 ID와 결과를 간단히 적어 둔다. AI 분석 중 상태와 완료/확인 필요 상태를 구분한다.

### 화면에 물품 ID가 보이지 않을 때

현재 관리자 상세 화면은 ID를 별도 글자로 보여주지 않는다. **앱 화면을 바꿀 필요 없이 읽기 전용 API로 ID를 확인**하고 PPT 사진 아래에 실제 확인한 ID를 적으면 된다.

1. 앱이 열린 브라우저에서 새 탭을 만든다. 같은 앱의 기본 주소 뒤에 `/api/items?sort=newest&limit=10`을 붙여 연다. 예를 들어 기본 주소가 `https://장치주소/`이면 `https://장치주소/api/items?sort=newest&limit=10`이다. 실제 내부 주소를 슬라이드에는 넣지 않는다.
2. JSON의 `items`에서 방금 등록한 물품의 `name`, `detected_at`, `id`를 찾는다. `Ctrl + F`로 물품 이름을 찾을 수 있다.
3. 이후에는 같은 기본 주소의 `/api/items/실제ID`를 열어 같은 물품을 조회한다. 이동·제거 뒤 이 탭을 새로고침해 동일 `id`, `status`, `updated_at` 등을 비교한다. 이는 조회만 하는 GET 요청이다.
4. S2–S4에는 실제 앱 화면을 넣고, 각 사진 아래에 **“기록 ID: 확인한 값”**이라고 별도 캡션을 추가한다. UI에 원래 표시된 값인 것처럼 이미지 안을 합성하지 않는다. 원시 JSON은 확인 기록으로 함께 보존한다.

ID를 확인하지 못했다면 ‘동일 ID 확인 완료’라고 쓰지 말고 사진·이름·물품 수를 관찰한 범위만 적는다.

### S2: 등록

1. 카메라 범위에 물품을 놓고 손을 뺀다.
2. 장면 안정화와 임시 등록을 기다린다. 물품 상세에서 이름·사진·상태를 확인하고 ID는 위의 읽기 전용 조회로 확인한다.
3. 실제 AI 이름·분류가 나왔으면 해당 결과를 기록한다. 확인 필요나 오류라면 그 상태를 그대로 남긴다. 화면에 ‘키 설정됨’이 있는 것만으로 원격 추론 성공으로 간주하지 않는다.
4. 해당 물품의 카드나 상세 화면을 잘라 `S2_added.png`로 저장한다.

### S3: 이동

1. 같은 물품을 카메라 안의 다른 위치로 옮기고 손을 뺀다.
2. 새 ID가 생겼는지, 기존 ID·물품 수·사진·위치가 어떻게 바뀌었는지 확인한다.
3. 해당 물품 화면을 `S3_moved.png`로 저장하고 읽기 전용 조회에서 **S2와 동일한 ID**인지 확인해 사진 아래 캡션으로 적는다. 물품 수가 늘거나 ID가 바뀌면 중복 방지 성공으로 쓰지 말고 원래 결과를 기록한다.

### S4: 제거

1. 같은 물품을 화면 밖으로 완전히 치운다.
2. 같은 기록이 회수 상태로 바뀌었는지 확인한다. 보관 목록에서 안 보이면 회수 필터나 활동 기록에서 해당 물품을 찾는다.
3. 이름·회수 상태나 활동 이력이 읽히는 영역을 `S4_removed.png`로 저장하고 동일 ID를 조회해 별도 캡션으로 적는다.
4. 이 사례의 ‘회수’는 **화면에서 사라졌다는 운영 상태**다. 실제 소유자 반환을 증명하는 장면으로 설명하지 않는다.

캡처 실패도 유용한 결과다. `expected / actual / 조건 / 재현 여부`를 적고 문제점 페이지에 반영한다.

## S5 — 실제 관리자 화면 / 15쪽

가장 쉬운 선택은 **실물 1개 이상이 등록된 대시보드**다. 실시간 카메라와 보관 현황을 한 화면에 담되 주소창은 제외한다. `S5_dashboard.png`로 저장한다. 화면 가로 폭은 1280px 이상을 권장하되 실제 브라우저에서 읽히는 배율을 사용한다.

관리 기능을 강조하고 싶으면 물품 상세 화면을 사용해도 된다. 이 경우 본인 테스트용 기록에서 이름·기한 편집을 확인한 뒤 실제 반영 화면을 캡처한다. 아직 확인하지 않은 메일 수신·기한 처리까지 성공했다고 설명하지 않는다. 새로운 Pi 실기를 마쳤다면 10·22쪽과 실기 확인표의 해당 상태도 함께 바꾼다.

기존 `output/maintenance/`의 브라우저 PNG는 **합성 카메라·임시 DB를 사용한 개발 화면**이다. 이를 대체 이미지로 쓰려면 슬라이드에 그 사실을 표시한다. 실제 Pi 화면인 것처럼 제목을 붙이지 않는다.

## 9쪽 — 공식 진행률 산정

첨부 목차는 백분율을 요구하지만, 팀·학교의 산정 기준과 최초 작업별 마감일은 아직 제공되지 않았다. 임의로 ‘90%’처럼 추정하지 않았다.

1. 최종 산출물을 작업 항목으로 나눈다. 예: 핵심 기능, Pi 배포, 실제 운영 검증, 정량 평가, 발표·문서.
2. 작업별 완료 기준을 문장으로 적는다. `코드 있음`과 `현장 시험 통과`는 서로 다른 기준이다.
3. 담당자와 가중치를 합의한다. 가중치 합은 100이 되도록 한다.
4. 가장 단순한 방식은 **완료한 작업의 가중치만 합산**하는 것이다. 진행 중 항목을 부분 인정하려면 판단 규칙을 먼저 정하고 분자와 분모를 보존한다.
5. `산정일 / 진행률 / 전체 작업 / 완료 기준`을 함께 기록해 9쪽을 채운다.

기능 구현이 많아도 미완료인 현장 검증·평가·최종 결과물을 분모에서 빼지 않는다. 10쪽의 코드 상태표를 프로젝트 전체 진행률 100%로 바꾸지 않는다. 원래 계획 마감일이 없으면 ‘일정 지연’ 대신 확인 가능한 변경 이유와 남은 작업을 설명한다.

## 19–20쪽 — 성능과 Baseline 값

- 먼저 **정답 라벨이 있는 평가 사건 수 N**, 물품 종류, 조명·거리·가림 조건, 모델·설정, 날짜를 확정한다.
- 사건 감지의 TP/FP/FN과 분류 정답 여부, uncertain·실패 응답을 따로 기록한다. 정확도·F1을 테스트 코드 통과율로 대체하지 않는다.
- 지연은 같은 사건의 행동 종료·DB 반영 시각을 연결해 계산한다. 카메라 상태 화면의 프레임 처리 시간은 종단간 사건 지연과 다르다.
- 분류 정확도는 정답 분류와 모델 응답을 비교하고 분모와 uncertain 처리 규칙을 먼저 정한다. 지연 p50/p95에는 표본 수와 시각 결측 여부도 함께 둔다.
- 성공 1건과 실패/불확실 1건을 제시할 때는 `같은 사건의 원본 사진 / 정답 / 실제 응답 / 원인 추정`을 함께 준비한다. 아직 원인이 확인되지 않았다면 추정이라고 표시한다.
- 20쪽의 B0/B1/B2/P1 비교는 같은 연속 영상, FPS, 워밍업, 후보 병합과 기준 갱신 규칙으로 수행할 계획이다. 현재 표는 초기 비교 결과가 아니라 **비교 설계**다.
- 기존 `experiments/pair_runner.py`는 안정 이미지 쌍의 detector core만 평가한다. 이 결과로 시간당 오탐, 실제 DB 중복 방지, 전체 시스템 지연을 주장하지 않는다. `plain` profile도 B0 순수 grayscale 차분과 다르다.
- 약 40건 파일럿은 기록·촬영 절차 점검을 위한 제안이다. 최종 평가 표본 수나 이미 확보한 데이터 수가 아니다.

이번 PPT 제작에서는 새 계측 코드, 유료 API 실험, 실제 Pi 실험을 수행하지 않았다. 상세 실험은 `docs/paper/EXPERIMENT_GUIDE.md`와 현재 코드 범위를 확인한 뒤 별도로 진행한다.
